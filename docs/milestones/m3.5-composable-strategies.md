# Milestone 3.5 — Composable Rules + Regime-Aware Strategy Selection

**Status:** Complete

## Goals

Milestone 3 shipped exactly one strategy shape: a hard-coded fast/slow SMA
crossover. This milestone makes strategy *logic* itself configurable, without
forcing every strategy into a rigid "one indicator per category, ANDed
together" mold, and adds market-regime detection as a first-class way to pick
*which* strategy logic is active — all while staying usable on instruments
other than crypto spot (CFDs, FX, indices) later, not just BTC/USDT.

Three deliverables, in order:

1. **A much bigger, curated indicator catalog** — trend, momentum,
   volatility, and volume indicators chosen for the strategy archetypes that
   actually get used in systematic trading (trend/breakout, pullback,
   mean-reversion, squeeze), not "every indicator anyone has ever heard of."
2. **`RuleStrategy`** — one config-driven strategy whose entry/exit are each
   an arbitrary AND/OR/NOT tree over any mix of indicators. A recipe can mix
   two volume checks and one volatility check, nest `(X OR Y) AND Z`, or
   drop volume checks entirely — no code changes, ever, for a new
   combination.
3. **`RegimeRouterStrategy`** — a meta-strategy that evaluates the same
   condition trees as `RuleStrategy` to detect market regime (e.g. `EMA50 >
   EMA200 AND ADX > 25 AND vol_percentile > 50` -> "trending breakout"), then
   activates the matching nested playbook. Regime detection is *strategy
   selection*, not a mandatory fourth gate bolted onto every recipe.

[`SmaCrossoverStrategy`](../../src/trading_platform/strategies/examples/sma_crossover.py)
remains the default config path (`config/default.yaml`) — nothing here
replaces it, it's an additional, more expressive strategy shape available
alongside it.

## Asset-Class-Agnostic Design (confirmed with the user before implementation)

The user plans to trade CFDs in addition to crypto later. Nothing in this
milestone assumes crypto-specific data or a spot-only, 24/7, volume-reliable
market:

- **Every indicator operates on plain OHLCV bars** — no funding rates,
  perpetual basis, open interest, or on-chain data anywhere in the catalog
  (explicitly deferred — see Known Gaps).
- **Price-normalized / scale-free measures are preferred in recipes and
  docs.** `atr_pct` (ATR ÷ close) and `bb_width` (band width ÷ mid) over raw
  ATR/raw band width, which are denominated in the instrument's own price
  units and meaningless to compare across a BTCUSDT chart and a 1.2345-quoted
  FX pair. `vol_percentile` ranks volatility against its *own* trailing
  history for the same reason. ROC/returns are percentages/fractions, not
  price deltas.
- **Volume is optional confirmation, never a hard dependency.** CFD/FX
  venues often report thin or meaningless volume. Every volume indicator
  (`rel_volume`, `volume_breakout`, `volume_roc`) accepts whatever
  `Bar.volume` the adapter supplies (including all-zero) and degrades to
  `NaN`/`False` rather than raising — see `indicators/rel_volume.py` etc. The
  worked regime/playbook examples below show volume leaves commented out as
  the "how to port this to a low-volume venue" pattern.
- **Direction is an execution concern, not an indicator/condition concern.**
  `compare`/`cross` work symmetrically for long or short setups; the
  condition DSL doesn't know or care that today's risk engine is long-only.
- **Sessions (RTH vs 24/7) are out of scope**, same as always — strategies
  already only see closed bars; a calendar/session adapter is a future,
  separate concern that doesn't require touching this DSL.

## Design Decisions (confirmed with the user before implementation)

1. **Composable condition trees, not "N indicators ANDed together."** The
   user explicitly rejected a fixed "one indicator per category" shape
   partway through planning ("I don't want this to be restrictive... some
   strategies might want two volume indicators and a volatility, some might
   want `X OR Y AND Z`"). The result is a small AST
   ([`strategies/rules/ast.py`](../../src/trading_platform/strategies/rules/ast.py)):
   `all`/`any`/`not` combinators over `compare`/`compare_indicators`/`cross`
   leaves, parsed from plain YAML mappings/lists
   ([`strategies/rules/parser.py`](../../src/trading_platform/strategies/rules/parser.py))
   — never `eval()`. Validated once at strategy construct time (unknown
   indicator names, bad operators, empty `all`/`any`), so a typo'd recipe
   fails immediately with a clear `ConditionError`, never mid-run.
2. **Kleene 3-valued evaluation, not plain `bool`.**
   ([`strategies/rules/evaluator.py`](../../src/trading_platform/strategies/rules/evaluator.py))
   A leaf whose indicator hasn't warmed up yet (`NaN`) evaluates to `None`
   ("not ready"), distinct from a real `False`. This matters concretely for
   `not`: if warmup-`NaN` were silently treated as `False`, `not: {compare:
   {indicator: adx, op: "<", value: 20}}` would spuriously read `True`
   ("ADX is confirmed NOT low") the instant a strategy starts, before ADX has
   any real value at all. `AllOf`/`AnyOf`/`NotOf` all propagate `None`
   correctly (`False` wins over `None` in `AllOf`; `True` wins over `None` in
   `AnyOf`; `not None is None`), and a strategy only ever fires on a
   confirmed `True`, never on `None`.
3. **Registry input profiles replace the `if name == "atr"` special case.**
   M2/M3 hard-coded exactly one exception in `DefaultStrategyContext.indicator`
   for ATR's `high`/`low` needs. With 30+ indicators now needing `close`-only,
   OHLC, OHLCV, or volume-only inputs, that pattern doesn't scale. Every
   registered indicator now declares an `InputProfile`
   (`close`/`ohlc`/`ohlcv`/`volume` —
   [`indicators/registry.py`](../../src/trading_platform/indicators/registry.py)),
   and `IndicatorRegistry.compute_from_bars(name, bars, **params)` extracts
   exactly the right series generically. `DefaultStrategyContext.indicator`
   is now three lines with zero per-indicator branching.
   **Breaking change to `IndicatorRegistry.compute`'s calling convention**
   (`compute(name, *series, **params)`, positional series in profile order,
   instead of always-`closes`-plus-ATR's-special `high=`/`low=` kwargs) —
   updated in the same PR along with its existing M2 tests; `compute_from_bars`
   is the primary interface going forward for anything driven by bars.
4. **Multi-line indicators register one name per output column.** MACD,
   Bollinger, Keltner, ADX/DI, Donchian, Supertrend, and Stochastic each
   compute a `pd.DataFrame` internally (e.g. `compute_macd` returns
   `macd`/`signal`/`hist` columns) but register N separate single-Series
   registry entries (`macd`, `macd_signal`, `macd_hist`, ...) via a small
   `_column(df_fn, column)` adapter, so `ctx.indicator("macd_hist", bars)`
   works exactly like every single-output indicator — no new calling
   convention for strategy authors, at the cost of recomputing the full
   indicator per requested line (same accepted "no streaming/incremental
   computation" trade-off as every indicator since M2).
5. **Shared Wilder smoothing helper.** RSI, ATR, and the new ADX all use
   Wilder's identical recursive smoothing formula; it was three near-copies
   before. Factored into
   [`indicators/wilder.py::wilder_smoothing`](../../src/trading_platform/indicators/wilder.py)
   and both `rsi.py`/`atr.py` refactored to call it — verified byte-for-byte
   identical output via the existing M2 test suite (no test changes needed
   for either besides the registry calling-convention update above).
6. **Regimes reuse the Part-A condition AST as `when` predicates — not a
   second DSL.** The user asked for regime detection to be "a huge part of
   strategy selection" as a related-but-separate concern in the same
   milestone. `RegimeRouterStrategy` parses a `when` condition per regime
   with the exact same parser/evaluator as `RuleStrategy`'s entry/exit, and
   each regime's `playbook.entry`/`playbook.exit` are literally nested
   `RuleStrategy`-shaped trees evaluated by the same `evaluate()` function.
   No duplicate logic, no second config schema to learn.
7. **First-match regime priority + `min_regime_bars` hysteresis.** Regimes
   are evaluated in list order; the first `when` that's `True` wins (so
   ordering *is* priority — documented, not implicit). `min_regime_bars`
   keeps a regime active for at least that many bars before a different
   `when` match is allowed to switch it out, preventing whipsaw on
   borderline bars. It does **not** delay the very first activation from the
   initial "nothing active" state — there's no whipsaw risk switching out of
   nothing.
8. **Safety-net flatten on regime switch, not "trust the old exit tree."**
   When the active regime changes (to a different regime, or to the
   `default: "flat"` state with no match), this strategy does not keep
   evaluating a playbook it just walked away from hoping its exit tree still
   makes sense for a different market regime. If a position is open at that
   moment, it emits an unconditional `CLOSE` immediately, tagged
   `metadata={"reason": "regime_switch", "new_regime": ...}`. Each regime's
   own entry/exit edge-state (`prev_entry`/`prev_exit`) resets on
   (re)activation, so a stale edge from a previous activation can never
   suppress a legitimate fresh signal the next time that regime comes back.
   A same-bar flatten `CLOSE` plus the newly-active regime's own `BUY` can
   both be emitted on the switching bar; `PassThroughRiskEngine`'s existing
   pending-order check means they never double-fire — the `BUY` is
   naturally deferred to the next bar once the `CLOSE` actually fills. No
   new risk-engine code was needed for this.
9. **`BUY`/`CLOSE` gated on `ctx.position_for`, edge-triggered on the
   condition tree.** Both `RuleStrategy` and each `RegimeRouterStrategy`
   playbook fire `BUY` only when `flat` **and** entry just transitioned
   `True` (not `False`/`None` -> `True`), and `CLOSE` only when **not**
   `flat` and exit just transitioned `True` — mirrors
   `SmaCrossoverStrategy`'s "one signal per transition, not every bar the
   condition holds" discipline, now generalized to any tree shape.

### Rule engine (`src/trading_platform/strategies/rules/`)

- `ast.py` — `Compare`, `CompareIndicators`, `Cross`, `AllOf`, `AnyOf`,
  `NotOf` frozen dataclasses; `Condition` type alias over all six.
- `values.py` — `IndicatorRef`/`CloseRef`/`ConstantRef` (`ValueSpec`), each
  with a `describe()` for human-readable trace metadata.
- `parser.py` — `parse_condition` (recursive-descent over YAML-loaded
  dicts/lists), `collect_indicator_names`/`validate_condition_indicators`
  (construct-time validation).
- `evaluator.py` — `evaluate(condition, bars, ctx, trace=None) ->
  bool | None`, Kleene 3-valued, with a `trace` mapping every fired leaf's
  `describe()` string to its result for `Signal.metadata`.
- `errors.py` — `ConditionError(StrategyError)`.

## Known Gaps (by design — later milestones or explicitly out of scope)

- **Not hand-verified line-by-line for every indicator.** Unlike M2's RSI
  (independently verified against a published third-party worked example),
  the more involved indicators added here (ADX, Supertrend, MACD, Keltner,
  realized_vol, vol_percentile) are tested via bounds/directionality/
  determinism/no-mutation on constructed scenarios rather than an
  independent hand-derived arithmetic trace of every recursive step. The
  simpler ones (Donchian, Bollinger, ROC, returns, rel_volume,
  volume_breakout, Stochastic, Wilder) do have hand-derived known-value
  assertions.
- **No incremental/streaming indicator computation** — same accepted
  trade-off as every indicator since M2; multi-line indicators (MACD,
  Bollinger, etc.) additionally recompute the *entire* underlying
  `DataFrame` once per requested output column per bar. Not a concern until
  a real per-bar latency budget exists (M6+ paper/live already tolerates
  this; would be revisited only if profiling ever shows it matters).
- **Regime `default` only supports `"flat"`.** Present as an explicit,
  validated param (`ValueError` on anything else) rather than silently
  ignored, so the schema has room to grow (e.g. a designated fallback
  playbook) without a breaking config change later — not built now because
  no concrete use case has asked for it yet.
- **No cycle detection in the condition AST.** Not missing — structurally
  unnecessary: `parse_condition` only ever builds a tree from nested
  YAML-loaded mappings/lists (no back-references, no shared mutable node
  identity), so a cycle cannot be constructed through this parser at all.
- **Session calendars, order-flow indicators (OBV/CMF), swing-structure
  detection, multi-asset correlation, and crypto-native inputs
  (funding/open interest/on-chain) remain explicitly deferred** — see the
  Asset-Class-Agnostic section above and the original milestone plan.
- **Still long-only.** The condition DSL is side-agnostic (a `cross`/`compare`
  works identically for a short setup), but `PassThroughRiskEngine` only
  ever sizes `BUY`s and closes with a `SELL`-side order — CFD short selling
  is a risk-engine change, not a rules-engine one, and stays out of scope
  here.
- **`RuleStrategy`/`RegimeRouterStrategy` playbooks share
  `SmaCrossoverStrategy`'s "edge-triggered, not sustained" signal
  philosophy.** If `entry` stays `True` for many bars without a position
  ever actually opening (e.g. the risk engine rejected the `BUY` for
  insufficient cash), neither strategy re-fires `BUY` until `entry` next
  transitions `False`/`None` -> `True` again. Documented in both classes'
  docstrings; consistent with the existing reference strategy, not a new
  inconsistency introduced here.
