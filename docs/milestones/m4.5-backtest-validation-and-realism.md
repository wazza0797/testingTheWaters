# Milestone 4.5 — Backtest Validation & Execution Realism

**Status:** Complete (Phases A + B). Phase C (walk-forward) deferred until
after Milestone 5 metrics exist for a meaningful optimizer objective.

**Depends on:** Milestone 4 (Backtesting Engine)

**Recommended before Phase C:** Milestone 5 (Performance Analytics)

## Goals

Close the two largest remaining **methodology** gaps in backtesting — without
yet building the full performance-analytics engine (that's M5):

1. **Anti-overfitting validation** — make in-sample vs out-of-sample
   comparison explicit, so tuning `strategy.params` against one full history
   and calling it "validated" is no longer the default workflow.
2. **Volatility-aware execution friction** — replace the static
   `spread_bps` assumption with a model that widens spread (and optionally
   tightens liquidity) when recent volatility is elevated, so backtests are
   not unrealistically optimistic exactly when real markets are hardest to
   trade.

This milestone deliberately does **not** include Sharpe/drawdown computation,
regime-split reporting, or statistical significance tests — those belong in
M5, which consumes `BacktestResult` as input. M4.5 produces **better runs**
and **better validation structure**; M5 produces **better interpretation**
of those runs.

## Background — why this exists

After M4 shipped (plus the robustness follow-up: cash-sufficiency guard, gap
warnings), three backtesting bias categories remain:

| Category | M4 status | This milestone |
|----------|-----------|----------------|
| Temporal look-ahead | ✅ Mitigated (latency, bar ordering) | — |
| Execution optimism (static spread) | ⚠️ Flat `spread_bps` | Phase B |
| Data-snooping / overfitting | ❌ Single full-history run | Phase A, C |
| Result misinterpretation | ❌ Headline return only | Deferred to M5 |

See `docs/architecture.md` §7 Limitations and Risks & Mitigations for the
full list including items explicitly out of scope here (point-in-time
instrument rules, tick-data simulation).

## Design Decisions (to confirm before implementation)

### 1. Validation modes — phased, not all-at-once

Three stages, each independently shippable:

| Phase | Mode | What it does | New deps |
|-------|------|--------------|----------|
| **A** | `hold_out` | Run backtest twice: in-sample `[start, train_end)` and out-of-sample `[test_start, end)`; print both summaries side-by-side | None |
| **B** | — | ATR-scaled spread in `SpreadModel` | `indicators/atr.py` (new) |
| **C** | `walk_forward` | Rolling windows: optimize params on IS window, run OOS with best params, slide, aggregate | Parameter grid search; M5 metrics strongly recommended |

**Recommendation:** Ship Phase A + B together (small, high value). Phase C
is a separate PR or sub-milestone once M5 can score each OOS window.

### 2. Hold-out date semantics

Match existing `load_bars` conventions (`start` inclusive, `end` exclusive):

```yaml
# config/backtest.yaml (new section)
validation:
  enabled: true
  train_end: "2025-01-01"    # in-sample ends here (exclusive)
  test_start: "2025-01-01"   # out-of-sample starts here (inclusive)
  # optional overrides; default to CLI --start/--end bounds
  test_end: null             # null = latest cached bar
```

- **In-sample (IS):** bars where `timestamp >= global_start AND timestamp < train_end`
- **Out-of-sample (OOS):** bars where `timestamp >= test_start AND timestamp < global_end`
- A gap between `train_end` and `test_start` is allowed (embargo period) —
  useful when signals have lookback (e.g. SMA-30 needs ~30 bars of warmup
  before OOS starts trading meaningfully).
- CLI prints a prominent banner: *"OOS results are the only ones that count
  for strategy validation — IS is for tuning only."*

### 3. Walk-forward shape (Phase C — design only for now)

```yaml
validation:
  mode: walk_forward
  walk_forward:
    is_bars: 8760          # ~1 year of 1h bars for optimization
    oos_bars: 2190         # ~3 months OOS per fold
    step_bars: 2190        # slide forward by OOS length
    param_grid:            # Cartesian product searched on IS only
      fast_period: [5, 10, 15, 20]
      slow_period: [20, 30, 40, 50]
    objective: total_return_pct   # until M5: simple; then Sharpe or Calmar
```

Output: table of OOS results per fold + aggregated OOS equity curve (stitched
from non-overlapping OOS segments only — never the IS segments).

**Optimizer scope:** Grid search only (no scipy/genetic optimizers). Keeps
dependencies zero and behaviour deterministic/reproducible.

### 4. Volatility-aware spread

Replace fixed `SpreadModel(spread_bps)` with optional ATR scaling:

```
effective_half_spread_bps = base_spread_bps/2 + k * (ATR / price) * 10000
```

- `base_spread_bps` — floor (current `spread_bps` default `5`)
- `spread_volatility_k` — multiplier (default `0` = disabled, backward compatible)
- `spread_atr_period` — lookback for ATR (default `14`)

`SpreadModel.fill_price(side, mid_price, bar, recent_bars)` needs recent bar
history. **`SimBroker`/`FillSimulator` maintain a rolling buffer** of the
last `spread_atr_period + 1` bars per symbol (backtest is single-symbol today,
so this is a simple list on `FillSimulator` or `BacktestEngine`).

When `spread_volatility_k == 0`, behaviour is identical to today (Phase B is
opt-in via config).

**Partial fills:** No change in Phase B. Optional future enhancement: reduce
`volume_participation_rate` in high-ATR regimes — deferred unless user asks.

### 5. CLI shape

Extend existing command rather than add a new one:

```bash
# Phase A — hold-out (enabled via config/backtest.yaml validation.enabled)
uv run trading-platform backtest

# Phase C — walk-forward (separate subcommand — long-running, different output)
uv run trading-platform walk-forward
```

`walk-forward` is its own subcommand because it runs many backtests and
prints a fold table — overloading `backtest` would be confusing.

| CLI | `main.py` — `walk-forward` subcommand | Long-running; prints fold table |
| Config | `ValidationConfig.walk_forward` nested block | IS/OOS/step bar counts, param grid |

## Tests

### Phase A
- `slice_bars` respects inclusive start / exclusive end
- `HoldOutValidator` runs two distinct bar ranges through the same engine wiring
- Empty IS or OOS range → clear error, not silent empty result
- Config disabled → `backtest` behaves exactly as M4 (regression)

### Phase B
- ATR matches known values on a fixed price series
- `spread_volatility_k=0` → identical fill prices to current `SpreadModel`
- High-ATR bar → wider effective spread than low-ATR bar at same mid price
- Backtest integration: fill prices differ when vol scaling enabled

### Phase C
- `ParamGrid` generates correct Cartesian product
- Optimizer picks best IS params on synthetic series where one param set is
  clearly superior
- Walk-forward produces N OOS segments with no IS bars leaking into OOS results
- Stitched OOS equity curve has no double-counting at fold boundaries

## Verification (manual, post-implementation)

1. Download ≥2 years of BTC/USDT 1h data.
2. Set `validation.train_end` / `validation.test_start` to split ~70/30.
3. Run `trading-platform backtest` — confirm IS and OOS summaries differ
   (they should — if identical, something is wrong or the strategy is
   trivially stable).
4. Enable `spread_volatility_k: 2.0`, rerun — confirm total fees paid
   increases vs flat spread (more conservative fills).
5. (Phase C) Run `trading-platform walk-forward` with a 2×2 param grid on
   6 months of data — confirm fold table prints and OOS aggregate differs
   from any single full-history run.

## Known Gaps (explicitly out of scope)

- **Purged / embargoed k-fold CV** — only needed once walk-forward + optimizer
  exist and signal lookback overlap becomes a concern; defer.
- **Point-in-time instrument rules** — separate infra milestone.
- **Performance metrics beyond `total_return_pct`** for optimizer objective
  until M5 ships (Phase C can launch with return-based objective, then upgrade).
- **Multi-symbol walk-forward** — M4 is single-symbol; same constraint applies.
- **Automatic "you tuned on OOS" detection** — can't enforce; documentation
  and banner only.

## Suggested Implementation Order

1. **Phase A** (~1–2 days) — hold-out validation; immediate anti-overfitting win.
2. **Phase B** (~1 day) — ATR + volatility spread; independent of Phase A.
3. **M5** — core analytics (Sharpe, drawdown, trade count).
4. **Phase C** (~2–3 days) — walk-forward + grid search, using M5 metrics as
   optimizer objective.

Phases A and B can ship in one PR or two; Phase C should wait for M5.
